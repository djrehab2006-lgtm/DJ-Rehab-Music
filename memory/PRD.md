- Audio engine (June 2026, SDK 58): `expo-audio` `createAudioPlaylist` (ExoPlayer on Android, <audio> on web). Background playback + lock-screen/notification controls (play/pause/next/prev, artwork = assets/track-icon.png via expo-asset) through `setActiveForLockScreen`; config plugin `expo-audio` with `enableBackgroundPlayback: true`, mic/RECORD_AUDIO disabled. `react-native-track-player`, `expo-av`, patch-package, index.native.js, service.js, player.tsx, context/AudioContext.tsx all REMOVED.
  - **THE ENGINE LIVES AT MODULE SCOPE: `app/utils/audioEngine.ts` (versionCode 5012). NEVER move players, listeners or queue/crossfade logic back into a React component.** Root cause of "music stops on a black screen, sometimes mid-song; same song shown paused when the app is reopened": Android destroys the Activity of a backgrounded app whenever it likes → React Native unmounts the component tree (JS runtime, expo AppContext and native players stay alive) → the old `AudioPlayerProvider` `useEffect` cleanup destroyed both decks mid-track (same finding as expo/expo#49906). Now: `usePlayerStore` (zustand) holds the UI state, the engine exports the controls, `initAudioEngine()` runs once per process (later mounts are no-ops), and `app/contexts/AudioPlayerContext.tsx` is a thin provider (store + favorites) with NO teardown on unmount.
  - Error recovery: expo-audio's `AudioPlaylist` never calls `prepare()` again after an ExoPlayer error, so a failed deck is dead (in-app Play did nothing before). `onDeckError` → current deck: `restartOnOtherDeck(position)` (other/new deck, same track + position, up to `MAX_RESTARTS` = 20 in a row, counter resets after 5s of progress or a track change; then waits for Play); other deck: that transition is played without overlap (`skipFadeIndex`). Dead decks are disposed lazily (`disposeDeck`) and never while they still carry the media session (= foreground service).
  - Every way of starting playback attaches the media session (`showOnLockScreen` / `activateLockScreen`); before 5012 Next/Previous right after app launch played WITHOUT the foreground service.
  - `__DEV__` only: `globalThis.__audioEngineDebug.failCurrentDeck()` / `.report()` to exercise recovery on web.
  - Known upstream expo-audio bugs NOT patched (would need patch-package + `expo.autolinking.android.buildFromSource: ["expo-audio"]` because expo-audio ships a prebuilt AAR): (1) lock-screen `MediaSession` only snapshots player state when (re)attached — `MetadataInjectingPlayer` listener uses Kotlin `by` delegation which drops all Java default methods (fixed upstream in expo/expo#52193, unreleased as of 58.0.12); likely cause of the open lock-screen/car "Track 1" issue. (2) playlist ExoPlayer has no `setWakeMode`.
- Local favorites & playlists (AsyncStorage + expo-file-system backup). Favorites: single source of truth is the audio context (`favoriteIds`/`removeFavorite`, AsyncStorage key `favorites`); Favorites tab reads from context (June 2026 fix — tab previously read a different key and was always empty)
- Resume Playback: last track, position, queue & shuffle state saved (AsyncStorage `last_playback_state`, via app/utils/playbackStateStorage.ts); restored PAUSED in mini-player on launch
- Local search over musicData
- Share button (native share sheet → Google Play URL)
- Target/compile SDK 36

- Crossfade (rebuilt June 2026, versionCode 5004 — TRUE OVERLAP): two native `AudioPlaylist` "decks" hold the same queue. `playerRef` = deck that owns the current track (UI + lock screen), `idleRef` = the other one (created lazily on first use, so crossfade OFF = old single-deck engine). ~20s before a track ends the idle deck is parked silently on the next track (`cueIdleDeck`); 4.3s before the end it starts playing at volume 0 (`startCrossfade`); once it is REALLY playing (`commitCrossfade`) it becomes the current deck (UI + `setActiveForLockScreen` move to it) and the two overlap for the rest of the outgoing track with equal-power curves; the outgoing deck is paused 0.25s before its end (`settleCrossfade`). Manual tap/next/prev/seek/pause/shuffle call `settleCrossfade()` first (hard cut, full volume). Toggle in Profile → Playback (AsyncStorage `crossfade_enabled`, default ON). Constants in `app/utils/crossfadeSettings.ts`.
  - **NO JS TIMERS in the audio engine.** Root cause of the listener bug (Galaxy S25 Ultra: volume ramps down, next track plays 1s then silence until phone is woken): fades were driven by `setInterval`, and React Native pauses JS timers on Android when the activity is paused / screen off (`JavaTimerManager.onHostPause`). Native → JS events still arrive in the background (expo-modules `emit` → `jsInvoker.invokeAsync`). Every fade step now runs inside `onStatus(deck, status)` from the native `playlistStatusUpdate` event (`updateInterval: 100ms`; React state is throttled to ~2/s via `publishStatus`).
  - Fail-safes: nothing is faded until the incoming deck reports real playback, so if it never starts the current deck just rolls into the next track natively at full volume (logged in diagnostics as "next track was not ready in time"); a parked deck that ever reports `playing` is paused again; solo deck volume is self-healed to 1.
  - Trade-offs to remember: while crossfade is ON the current deck still natively pre-buffers its own next track (~45s of audio downloaded twice per track); the lock-screen/Bluetooth session is re-created on the other deck at every crossfade.
  - Idle deck's native queue is rebuilt lazily (`queueVersionRef` / `deckVersionRef`) the next time it is cued after the queue changed.

- What's New pop-up: built then REMOVED at user request (June 2026). Files deleted (WhatsNewModal.tsx, whatsNew.ts). Do not re-add unless asked.

## Build 5015 (car screen follows automatic track changes) — native only, NOT YET VERIFIED IN A CAR
- Report on 5014: phone lock screen steady and correct, crossfade fine, but the car (Bluetooth) only showed the new song after a manual skip.
- Cause found in the patch itself (not proven on a device): every `AudioPlaylist` deck owned a live "basic" MediaSession. A fresh deck that starts playing silently for a crossfade became a second PLAYING session of the app, Android's Bluetooth service switches its controller to the newest playing session of a package, the hand-over (`MediaSession.setPlayer`) then happened on the lock screen session while Bluetooth was listening to the other one, and when it comes back it does not re-read anything until the session reports a change (= a manual skip).
- Patch changes (`patches/expo-audio+58.0.10.patch`):
  1. `AudioPlaylist.kt`: the basic session is released right after it is built (constructor + `assignBasicMediaSession`), so the app only ever has ONE session: the playback service's.
  2. `AudioControlsService.kt`: 1s and 3s after every hand-over `announceSessionState` calls `updateSessionCustomLayout` again (same buttons → Media3 re-publishes the legacy PlaybackState; nothing visible on the phone). A Bluetooth controller that missed the hand-over sees a state that differs from what it last sent and pushes the current track to the car.
- Checked against Media3 1.9.1 source: `setPlayer` already runs `onMediaItemTransition` → `setMetadata` + `setPlaybackState(activeQueueItemId)` on the legacy session, so no fake player events are needed. The Kotlin was NOT compiled in this container (small edits only).
- If the car is still wrong after 5015: ask whether it fails on EVERY automatic change or only the first one after starting the app, and for the Profile → Lock screen controls report. Next idea: one permanent session player whose inner deck is swapped and which emits a seek-style `onPositionDiscontinuity` + `onMediaItemTransition`, so a hand-over is identical to a manual skip.

## Build 5018 (lock screen / car titles: ROOT CAUSE FOUND from the phone's report) — JS only, NOT YET VERIFIED ON A DEVICE
- Report on 5017 (screenshot of Profile → Lock screen controls, Samsung SM-S156V, Android 16): `Last activation error: Call to function 'AudioPlaylist.setActiveForLockScreen' has been rejected … Cannot cast value for field 'artworkUrl' ('class java.net.URL?') … java.net.MalformedURLException: no protocol: assets_trackicon`, `Artwork URL: assets_trackicon`, `Lock screen activations: 23`, `Playback restarts: 20`, `Playing: false`.
- **Cause (reproduced with the real engine, see `/app/tools/audio-engine-test`):** in an installed build (APK/AAB) `Asset.fromModule(TRACK_ICON).downloadAsync()` (expo-asset 58.0.19) returns the Android resource NAME `assets_trackicon` as `localUri`/`uri`, not a URL. expo-audio converts `artworkUrl` to `java.net.URL` before the native function body runs, so EVERY call carrying it is refused, title included. `activateLockScreen` had a retry without artwork (since 5003), `showOnLockScreen` → `updateLockScreenMetadata` did not and swallowed the error. Result on a phone: the title only changed when the controls were (re)attached (first play, crossfade hand-over, queue rebuilt) and stayed stale for Next/Previous (app, lock screen, car, headset), tapping another song of the same list, and automatic changes without crossfade. In development the address is `file://…`, so it never showed in preview/Expo Go. Present in every installed build since 5001; the native patch work of 5014–5017 was aimed at the wrong layer.
- Fix (`app/utils/audioEngine.ts` only, native patch unchanged from 5017):
  1. `usableArtwork()`: `artworkUrl` is only sent when it is `http(s)://` or `file://`; otherwise omitted. Installed builds therefore show NO artwork on the lock screen (same as before in practice: only the no-artwork retry ever succeeded).
  2. `showOnLockScreen`: a refused `updateLockScreenMetadata` is logged, recorded as `Last lock screen error`, and falls back to `activateLockScreen`.
  3. Report: new `Build: <version> (<versionCode>)` line (tells which build produced a report — the user often builds stale code), `Lock screen title updates` counter, `Lock screen artwork` line.
- Verified here: `/app/tools/audio-engine-test/run.sh` — before the fix 6 of 8 track-change checks FAIL in installed-build mode with the phone's exact error text and report header; after the fix all pass in installed-build mode, development mode and with all updates refused (fallback). Native side of `updateLockScreenMetadata` is covered by the Robolectric rig (`ServiceTest`, "manual skip"). NOT verified: a phone, a car.
- Not addressed / open:
  - `Playback restarts: 20` + `Playing: false` in the same report = 20 failed restarts in a row then gave up (MAX_RESTARTS). Most likely the phone had no internet for a while (status bar shows no mobile service), but the error codes are only in the log part of the report, which the screenshot did not include. Ask for the SHARED report text (Share button) if playback stops again.
  - Whether the car follows AUTOMATIC crossfade changes is still unconfirmed on a device (5015–5017 native work targets it; rig says the session is correct).
  - Lock screen artwork in installed builds: would need a real `file://` copy of the icon (expo-asset's native `downloadAsync` can produce one; its JS wrapper skips it for bundled images). Deliberately not done in 5018 to avoid a new variable; offer as a feature.
